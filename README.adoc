= Webtrees MCP Server

Webtrees MCP Server is a read-only https://modelcontextprotocol.io/[Model Context Protocol (MCP)] server written in Go. It connects to a MariaDB database used by https://www.webtrees.net/[webtrees] and lets MCP clients retrieve structured genealogy data.

This is an early, AI-assisted project. The implementation has not been independently audited or tested against every webtrees release. Review the code and run it with least-privilege, read-only database credentials before using it with real family data. See `SECURITY.adoc` for deployment and privacy considerations.

== Features

* Runs over the MCP stdio transport for use by local agent clients.
* Exposes `get_person`, `search_persons`, `get_family`, `list_tree_ids`, `list_recently_born`, and `list_recently_deceased` tools.
* Parses names, family links, events, qualified dates, places, notes, and source references from webtrees GEDCOM records.
* Performs only parameterized `SELECT` queries; it has no write or migration operations.
* Supports configurable webtrees table prefixes.

== Database schema essentials

The webtrees table prefix defaults to `wt`. The dump used during development confirms these are the core tables for genealogy queries:

|===
|Table |Required columns |Purpose

|`wt_gedcom` |`gedcom_id`, `gedcom_name`, `title` |Tree catalog; `gedcom_id` is the numeric tree ID.
|`wt_individuals` |`i_id`, `i_file`, `i_gedcom` |Individual xref, tree ID, and raw GEDCOM record.
|`wt_families` |`f_id`, `f_file`, `f_husb`, `f_wife`, `f_gedcom` |Family xref, tree ID, spouses, and raw family GEDCOM record.
|`wt_dates` |`d_gid`, `d_file`, `d_type`, `d_year`, `d_month`, `d_day` |Indexed event dates for efficient date-based queries.
|`wt_link` |`l_file`, `l_from`, `l_type`, `l_to` |Generic GEDCOM relationship links.
|`wt_name` |`n_file`, `n_id`, `n_full`, `n_surname`, `n_givn` |Normalized/searchable names.
|`wt_sources` |`s_id`, `s_file`, `s_name`, `s_gedcom` |Source records and citations.
|===

`i_file` and `f_file` refer to `wt_gedcom.gedcom_id`. Individual and family details are stored primarily as GEDCOM text, while `wt_dates`, `wt_name`, and `wt_link` provide useful indexes for future tools. Queries must always constrain records by the tree ID because xrefs such as `I1` and `F1` are only unique within a tree.

Useful future read-only tools include family/relative expansion from `wt_families`, ancestor and descendant traversal through `FAMC`/`FAMS` and `f_husb`/`f_wife`/`f_gedcom`, date-range searches via `wt_dates`, name searches via `wt_name`, and evidence lookup through `wt_sources`.

== Requirements

* Go 1.25 or newer (the MCP dependency currently requires Go 1.25.5).
* A MariaDB/MySQL database containing a webtrees installation.

== Running

Build or run the server with a webtrees DSN:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees'
----

The table prefix defaults to `wt` and can be changed with `-prefix`:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -prefix wt
----

The server reads MCP messages from standard input and writes protocol responses to standard output. Diagnostic errors are written to standard error.

HTTP is disabled by default. Enable the streamable HTTP transport explicitly with `-http`; it binds to `127.0.0.1` on port `8080` by default and uses the `/mcp` endpoint:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -http
----

The HTTP transport is stateless, so clients do not need to preserve an `Mcp-Session-Id` header between requests.

For troubleshooting, `-http-debug` logs request and response headers and bodies to standard output. This may include genealogy data or credentials, so enable it only temporarily in a trusted environment:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -http -http-debug
----

For Docker or Podman port publishing, bind to all container interfaces:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -http -http-host 0.0.0.0
----

`-http-host` also accepts a specific interface or IP address. Binding to `0.0.0.0` or a public address is not recommended without authentication, firewall rules, and transport security because the HTTP endpoint exposes genealogy data.

Use `-http-port` to select another port:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -http -http-port 9090
----

== MCP tools

To enumerate the registered tools, call `tools/list` after `initialize` with an empty parameter object (or omit `params`):

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {}
}
----

The `protocolVersion`, `capabilities`, and `clientInfo` fields belong to `initialize`; they are not needed for `tools/list`. If a response contains `nextCursor`, send that exact opaque value in a later `tools/list` request. Do not send a placeholder such as `optional-cursor-value`: the server expects a framework-generated base64 cursor and will reject an invalid value.

`get_person` accepts:

[source,json]
----
{
  "tree_id": "tree-id",
  "person_id": "I1"
}
----

`search_persons` accepts `tree_id` and `surname`, and returns matching person summaries. `get_family` accepts `tree_id` and `family_id`, returning parent and child links without embedding duplicate person objects.

`list_tree_ids` takes no arguments. The born and deceased listing tools accept a `tree_id` and optional `limit` (default `10`). All people returned include parsed identifying details where available. Relative entries are intentionally links only, containing `person_id` and optional `url` and `relationship` fields; they do not embed another person object.

It returns JSON in this shape:

Tool results carry the native payload in `structuredContent` and a concise,
human-readable summary in `content`. The summary uses available genealogy
fields such as names, identifiers, dates, occupations, relationships, and
family links; unavailable details such as event places or marriage dates are
not invented.

Successful tool results always include a JSON-object `structuredContent` value.
Collection results are wrapped in named fields such as `people` or `trees`
instead of returning a top-level array, which improves compatibility with
strict MCP clients. Error results contain diagnostic `content` and do not
claim to have successful structured data.

[source,json]
----
{
  "id": "I1",
  "name": {
    "given": "Ada",
    "surname": "Lovelace"
  },
  "birth_date": "10 DEC 1815",
  "events": [
    {
      "type": "birt",
      "date": {
        "raw": "10 DEC 1815",
        "precision": "exact"
      },
      "place": "London"
    }
  ]
}
----

The following response examples use fictional data. A person result includes
both a readable summary and the native structured payload:

[source,json]
----
{
  "content": [
    {
      "type": "text",
      "text": "Person \"Ada Mayer\" (I44) was born on 1982 and died on 2026. They worked as Carpenter. Associated people: I45 (spouse), I46 (child), I47 (child)."
    }
  ],
  "structuredContent": {
    "id": "I44",
    "name": {
      "given": "Ada",
      "surname": "Mayer"
    },
    "birth_date": "1982",
    "death_date": "2026",
    "occupation": "Carpenter",
    "relatives": [
      {
        "person_id": "I45",
        "relationship": "spouse"
      },
      {
        "person_id": "I46",
        "relationship": "child"
      },
      {
        "person_id": "I47",
        "relationship": "child"
      }
    ]
  }
}
----

Family results summarize the available links without inventing names or event
details that are not part of the returned family data:

[source,json]
----
{
  "content": [
    {
      "type": "text",
      "text": "Family F12 has parents I44 and I45; children: I46, I47."
    }
  ],
  "structuredContent": {
    "family_id": "F12",
    "parents": [
      {"person_id": "I44", "relationship": "parent"},
      {"person_id": "I45", "relationship": "parent"}
    ],
    "children": [
      {"person_id": "I46", "relationship": "child"},
      {"person_id": "I47", "relationship": "child"}
    ]
  }
}
----

List and search tools use the same pattern. For example, a fictional surname
search might return this summary:

[source,json]
----
{
  "content": [
    {
      "type": "text",
      "text": "Found 2 people matching surname \"Mayer\". Person \"Ada Mayer\" (I44) was born on 1982. Person \"Bruno Mayer\" (I48) has no recorded birth date."
    }
  ],
  "structuredContent": {
    "people": [
      {
        "id": "I44",
        "name": {"given": "Ada", "surname": "Mayer"},
        "birth_date": "1982"
      },
      {
        "id": "I48",
        "name": {"given": "Bruno", "surname": "Mayer"}
      }
    ]
  }
}
----

== Project layout

* `internal/db` contains the read-only database repository.
* `internal/domain` contains database- and transport-neutral genealogy entities.
* `internal/genealogy` defines the repository port used by application code.
* `internal/db` contains the SQL adapter and lightweight GEDCOM parser.
* `internal/mcp` maps repository operations to MCP tools.
* `test` contains sqlmock unit tests and an optional database schema test.

== Testing

Run unit and integration-test packages with:

[source,shell]
----
go test ./...
go vet ./...
----

The schema test is skipped unless `WEBTREES_DSN` is set:

[source,shell]
----
WEBTREES_DSN='user:password@tcp(127.0.0.1:3306)/webtrees' go test ./test -run TestWebtreesSchema
----
