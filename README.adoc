= Webtrees MCP Server

Webtrees MCP Server is a read-only https://modelcontextprotocol.io/[Model Context Protocol (MCP)] server written in Go. It connects to a MariaDB database used by https://www.webtrees.net/[webtrees] and lets MCP clients retrieve structured genealogy data.

This is an early, AI-assisted project. The implementation has not been independently audited or tested against every webtrees release. Review the code and run it with least-privilege, read-only database credentials before using it with real family data. See `SECURITY.adoc` for deployment and privacy considerations.

== Features

* Runs over the MCP stdio transport for use by local agent clients.
* Exposes `get_person_by_exact_id`, `search_person_by_name`, `get_family_by_exact_id`, `relationship_path`, `get_ancestors`, `get_descendants`, `search_events`, `list_recently_born`, and `list_recently_deceased` tools.
* Parses names, family links, events, qualified dates, places, notes, and source references from webtrees GEDCOM records.
* Performs only parameterized `SELECT` queries; it has no write or migration operations.
* Supports configurable webtrees table prefixes.

== Database schema essentials

The webtrees table prefix defaults to `wt`. The dump used during development confirms these are the core tables for genealogy queries:

|===
|Table |Required columns |Purpose

|`wt_gedcom` |`gedcom_id`, `gedcom_name`, `title` |Tree catalog; `gedcom_id` is the numeric tree ID.
|`wt_individuals` |`i_id`, `i_file`, `i_gedcom`, `i_sex`, `i_birth_year`, `i_death_year` |Individual xref, indexed sex/year fields, and raw GEDCOM record.
|`wt_families` |`f_id`, `f_file`, `f_husb`, `f_wife`, `f_gedcom` |Family xref, tree ID, spouses, and raw family GEDCOM record.
|`wt_dates` |`d_gid`, `d_file`, `d_type`, `d_year`, `d_month`, `d_day` |Indexed event dates for efficient date-based queries.
|`wt_link` |`l_file`, `l_from`, `l_type`, `l_to` |Generic GEDCOM relationship links.
|`wt_name` |`n_file`, `n_id`, `n_full`, `n_surname`, `n_givn` |Normalized/searchable names.
|`wt_sources` |`s_id`, `s_file`, `s_name`, `s_gedcom` |Source records and citations.
|===

`i_file` and `f_file` refer to `wt_gedcom.gedcom_id`. Individual and family details are stored primarily as GEDCOM text, while `wt_dates`, `wt_name`, and `wt_link` provide useful indexes for future tools. Queries must always constrain records by the tree ID because xrefs such as `I1` and `F1` are only unique within a tree.

The `search_events` tool uses `wt_dates` for indexed individual-event filtering.
It accepts an optional `event_type` such as `BIRT` or `DEAT`, inclusive
`from_date` and `to_date`, a case-insensitive place substring, and bounded
`limit`/`offset` pagination. Results include the matching person ID, event
type, source date text, and place; use `get_person_by_exact_id` to inspect full event
evidence. Family events and event places not represented by the date index are
not returned by this tool.

Useful future read-only tools include family/relative expansion from `wt_families`, ancestor and descendant traversal through `FAMC`/`FAMS` and `f_husb`/`f_wife`/`f_gedcom`, name searches via `wt_name`, and evidence lookup through `wt_sources`.

== Requirements

* Go 1.25 or newer (the MCP dependency currently requires Go 1.25.5).
* A MariaDB/MySQL database containing a webtrees installation.

== Running

Build or run the server with a webtrees DSN:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -tree-id=1
----

The table prefix defaults to `wt` and can be changed with `-prefix`:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -prefix wt -tree-id=1
----

The server reads MCP messages from standard input and writes protocol responses to standard output. Diagnostic errors are written to standard error.

HTTP is disabled by default. Enable the streamable HTTP transport explicitly with `-http`; it binds to `127.0.0.1` on port `8080` by default and uses the `/mcp` endpoint:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -tree-id=1 -http
----

The HTTP transport is stateless, so clients do not need to preserve an `Mcp-Session-Id` header between requests.

At startup the server verifies database connectivity with a five-second
timeout. If that check or the HTTP listener fails, the process exits non-zero
and logs the reason. `GET /healthz` is a liveness check and
`GET /readyz` is a readiness check; both return only a small status JSON
object and never include the DSN or genealogy data. The process handles
`SIGINT` and `SIGTERM` and allows in-flight HTTP requests up to ten seconds to
finish before closing the database.

For troubleshooting, `-http-debug` logs request and response headers and bodies to standard output. Body logging is limited to 4096 bytes per message by default; use `-http-debug-body-limit` to change the limit (including `0` to disable body contents). Authorization, proxy-authorization, cookie, and set-cookie headers are redacted by default. Use `-http-debug-redact-headers` with a comma-separated list to customize the redactions; an empty value disables header redaction. These controls do not redact URLs or body contents, so enable debug logging only temporarily in a trusted environment:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -tree-id=1 -http -http-debug
----

For Docker or Podman port publishing, bind to all container interfaces:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -tree-id=1 -http -http-host 0.0.0.0
----

`-http-host` also accepts a specific interface or IP address. Binding to `0.0.0.0` or a public address is not recommended without authentication, firewall rules, and transport security because the HTTP endpoint exposes genealogy data.

Use `-http-port` to select another port:

[source,shell]
----
go run . -dsn 'user:password@tcp(127.0.0.1:3306)/webtrees' -tree-id=1 -http -http-port 9090
----

== MCP tools

To enumerate the registered tools, call `tools/list` after `initialize` with an empty parameter object (or omit `params`):

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {}
}
----

The `protocolVersion`, `capabilities`, and `clientInfo` fields belong to `initialize`; they are not needed for `tools/list`. If a response contains `nextCursor`, send that exact opaque value in a later `tools/list` request. Do not send a placeholder such as `optional-cursor-value`: the server expects a framework-generated base64 cursor and will reject an invalid value.

`get_person_by_exact_id` accepts an exact GEDCOM individual ID; it never accepts a human name:

[source,json]
----
{
  "person_id": "I1"
}
----

All tools query the numeric tree selected at startup with `-tree-id=1`; they do
not accept a `tree_id` input. `search_person_by_name` requires a non-blank
string `surname`.
It also accepts optional indexed `given_name` and `sex` fragments, inclusive
`birth_year_min`, `birth_year_max`, `death_year_min`, and `death_year_max`
bounds. `match_mode` controls name matching: `exact` uses indexed equality,
`prefix` uses an indexed prefix (the default), and `fuzzy` uses a bounded
indexed-prefix candidate set followed by deterministic Levenshtein matching
with a maximum distance of 2. Fuzzy searches can miss candidates outside the
bounded candidate set. Surrounding whitespace is ignored. Optional pagination uses integer
`limit` (default `10`, allowed range `1`-`100`) and `offset` (default `0`,
allowed range `0`-`10000`). Invalid values and reversed year bounds are
rejected. Candidate selection is performed by `wt_name` and indexed individual
fields; it does not scan raw GEDCOM records. Returned IDs are research leads;
chain them into `get_person_by_exact_id` for verification. The deprecated
`include_indirect` option is accepted for compatibility but cannot enable raw
GEDCOM matching in this indexed search.
`get_family_by_exact_id` accepts `family_id`, returning parent links and child
records with available `person_id`, `name`, `birth_year`, and `sex` values
without embedding duplicate person objects.

`relationship_path` accepts `from_person_id` and `to_person_id`.
It follows explicit family links for a bounded shortest-path search and returns
each hop with its `family_id` evidence and relationship kind. A missing path is
reported with `found: false`; surnames and inferred relationships are not used.

`get_ancestors` and `get_descendants` accept a starting `person_id` and optional
`max_depth` (default `5`, maximum `20`) and `limit`
(default `100`, maximum `500`). They traverse only explicit family links and
return a bounded flat list of people with generation depth, relationship, and
the `via_family_id` evidence. A `truncated` result means the configured limit
was reached; it does not mean the line is complete.

`search_events` prefers ISO dates such as `1815-12-10`. It also accepts a year
(`1815`), year and month (`1815-12`), slash-separated variants, common textual
dates such as `10 DEC 1815`, and GEDCOM qualifiers such as `ABT` and `BET`.
Date ranges are inclusive; an omitted boundary is unbounded. Year-only index
entries remain year-precision results, and place matching is a case-insensitive
substring match rather than an exact normalized-place query.

The born and deceased listing tools accept `limit` and `offset`. Limits default to
`10` and are capped at `100`; offsets default to `0`. Recent-person lists are
ordered by event year descending and person ID ascending as a deterministic
tie-breaker. Request the next page by increasing `offset` by the previous
`limit`. All people returned include parsed identifying details where available.
Relative entries are intentionally links only, containing `person_id` and
optional `url` and `relationship` fields; they do not embed another person object.

=== Choosing and chaining tools

The tree ID is fixed by the startup `-tree-id` argument. Use
`search_person_by_name` when starting from a name; it returns direct name matches by default. Set
`include_indirect` only when investigating broad GEDCOM-record matches, and
check each result's `match.direct_hit` before using it. Chain a selected
`person_id` into `get_person_by_exact_id` for complete event, family-link, note, and
source detail. Use `get_family_by_exact_id` when a family ID is known, then chain its
parent and child IDs into `get_person_by_exact_id`. The recent-birth and recent-death
tools are rankings by parsed year, not proof that the event is historically
the latest; inspect the detailed person events before making that claim.

Every successful tool result has a concise, line-oriented human-readable `content` summary
and an object-shaped `structuredContent` value matching the tool's advertised
output schema. Collection results are wrapped in `people` or `trees`. Error
results use diagnostic `content` and should not be treated as successful
structured data. Missing or uncertain facts must be reported as such.

=== Published output schemas

The server publishes these schemas through `tools/list` and returns the same
object shapes in `structuredContent`:

* `get_person_by_exact_id`: an object with `id`, `name`, and optional dates, alternate names,
  events, family links, relatives, notes, sources, and search-match metadata. Family
  links include the exact `family_id` and `role`; child links include resolved parent
  IDs, names, and roles, while spouse links include the resolved spouse and child count
  when available.
* `search_person_by_name`: `{ "people": [person], "total_count": 42,
  "has_more": true, "limit": 10, "offset": 0 }`. `total_count` is the
  number of matching indexed candidates; `has_more` indicates whether another
  page exists at the requested offset and limit.
* `list_recently_born` and `list_recently_deceased`: `{ "people": [person] }`.
* `search_events`: `{ "events": [{"person_id", "type", "date", "place"}] }`.
* `get_family_by_exact_id`: an object with `family_id` and optional `parents`, `children`,
  `events`, `notes`, and `sources`.
* `get_ancestors` and `get_descendants`: `{ "root_person_id": "I1",
  "direction": "ancestors", "nodes": [{"person_id", "depth",
  "via_family_id", "relationship", "person"}], "truncated": false }`.

IDs are stable within a tree. Collection results are named objects rather than
top-level arrays, so clients can validate them against the published schemas
and chain returned IDs into detail tools.

It returns JSON in this shape:

Tool results carry the native payload in `structuredContent` and a concise,
human-readable summary in `content`. The summary uses stable labels and one
fact per line so that models can extract facts without parsing prose. Person
events use their GEDCOM tags (for example `BIRT`, `DEAT`, and `OCCU`) and include
available dates and places; unavailable details are not invented. For example:

[source,text]
----
Person: Casey Example (I7)
Events:
- BIRT: 1 JAN 1900 in Exampletown
- DEAT: 15 MAY 1950
- OCCU: Software Engineer
----

The text form is deliberately the primary factual representation for small
local models (assume at best `qwen2.5:14b-instruct` on a consumer PC). Such
models may ignore `structuredContent` and may hallucinate facts when a summary
is incomplete. Every available fact must therefore appear in `content` using
stable labels and explicit lists. Keep one fact per line, preserve exact and
uncertain source values, identify stable IDs and GEDCOM tags, and explicitly
state missing facts or research-lead limitations. Do not replace a list of
facts with a fluent summary or a count.

Successful tool results always include a JSON-object `structuredContent` value.
Collection results are wrapped in named fields such as `people` or `trees`
instead of returning a top-level array, which improves compatibility with
strict MCP clients. Error results contain diagnostic `content` and do not
claim to have successful structured data.

[source,json]
----
{
  "id": "I1",
  "name": {
    "given": "Ada",
    "surname": "Lovelace"
  },
  "birth_date": "10 DEC 1815",
  "events": [
    {
      "type": "birt",
      "date": {
        "raw": "10 DEC 1815",
        "precision": "exact"
      },
      "place": "London"
    }
  ]
}
----

== Project layout

* `internal/db` contains the read-only database repository.
* `internal/domain` contains database- and transport-neutral genealogy entities.
* `internal/genealogy` defines the repository port used by application code.
* `internal/db` contains the SQL adapter and lightweight GEDCOM parser.
* `internal/mcp` maps repository operations to MCP tools.
* `test` contains sqlmock unit tests and an optional database schema test.

== Testing

Run unit and integration-test packages with:

[source,shell]
----
go test ./...
go vet ./...
----

The schema test is skipped unless `WEBTREES_DSN` is set:

[source,shell]
----
WEBTREES_DSN='user:password@tcp(127.0.0.1:3306)/webtrees' go test ./test -run TestWebtreesSchema
----
